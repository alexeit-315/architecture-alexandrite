## Мотивация

Основные проблемы системы:
1. Долгая загрузка списка заказов (критично для операторов)
2. Проблемы с API для партнеров
3. Медленный расчет стоимости

Бизнес-последствия:
1. Потеря крупных контрактов
2. Рост недовольства B2C и B2B клиентов
3. Проблемы с мотивацией операторов

Анализ системы показывает, что основные узкие места связаны с:
1. Частыми запросами списка заказов в MES
2. Обновлением статусов заказов
3. Доступом к данным о заказах из разных компонентов системы

Кеширование позволит:
1. Уменьшить нагрузку на базы данных MES db и MES Cost calculating service db
2. Снизить время отклика при работе со списком заказов
3. Ускорить отображение актуальной информации о статусах заказов для B2C и B2B клиентов

Элементы системы для кеширования:
1. Список заказов из MES API  
- Кеширование с учетом пагинации и фильтров
- Отдельные ключи для разных ролей (операторы/API пользователь)
2. Статусы заказов из MES API 
- Раздельные кеш-зоны для разных клиентов
- Автоматическое обновление популярных запросов
3. Информация о расчетах стоимости из MES Cost calculating service
- Кеширование промежуточных результатов расчета
- Инвалидизация по изменению 3D-модели (хеш файла)
4. Данные для партнерского API
- Индивидуальные TTL для разных типов партнеров
- Приоритетное кеширование для ключевых партнеров

## Предлагаемое решение

Планируется использовать серверное кеширование 

Выбор серверного кеширования обусловлен:
1. Централизованным управлением кешем
2. Возможностью инвалидации кеша при изменениях
3. Снижением нагрузки на базу данных
4. Уменьшением времени отклика для всех клиентов
5. Возможностью интеграции с существующей системой мониторинга
 

### Стратегии кеширования  

| **Тип данных**          | **Стратегия**               | **TTL**       | **Инвалидизация**              |
|:------------------------|:----------------------------|:--------------|:-------------------------------|
| Список заказов          | Cache-Aside + Read-Through  | 60 секунд     | По событию из RabbitMQ + TTL   |
| Статусы заказов         | Write-Through + Event-based | 15 минут      | При изменении статуса + TTL    |
| Расчеты стоимости       | Write-Behind                | 24 часа       | По изменению 3D-модели + TTL   |
| Данные партнерского API | Cache-Aside                 | 30-300 секунд | Принудительно по запросу + TTL |

Выбор паттерна кеширования обусловлен:
1. Cache-Aside (для списков заказов и партнерского API)
- Позволяет загружать данные в кеш только при необходимости
- Минимизирует запросы к БД для редко запрашиваемых данных
- Прост в реализации и отладке
- Хорошо сочетается с существующей архитектурой
- Эффективен для данных с предсказуемым шаблоном доступа
2. Write-Through (для статусов заказов)
- Гарантирует актуальность данных в кеше
- Упрощает логику приложения
- Уменьшает нагрузку на БД при частых чтениях
- Сочетается с event-based инвалидацией через RabbitMQ
3. Write-Behind (для расчетов стоимости)
- Позволяет буферизировать запросы к БД
- Уменьшает задержки при записи
- Оптимален для ресурсоемких операций расчета
- Сочетается с длительным TTL и инвалидацией по данным

Альтернативные паттерны:
1. Write-Through: 
- Не подходит из-за разнородности источников данных
- Усложняет систему при наличии нескольких БД
- Менее гибкий в настройке политик кеширования
2. Refresh-Ahead: 
- Не подходит из-за избыточности для большинства сценариев
- Требует точного прогнозирования запросов
- Может создавать избыточную нагрузку

### Стратегии инвалидизации

| **Тип**              | **Применение**              | **Преимущества**                          | **Недостатки**                  |
|:---------------------|:----------------------------|:------------------------------------------|:--------------------------------|
| По событию           | Статусы заказов             | Мгновенная актуальность                   | Сложная отладка                |
| По времени (TTL)     | Все данные                  | Простота реализации                       | Возможное устаревание          |
| По ключу             | Партнерский API             | Точечное управление                       | Требует точного знания ключей  |
| По запросу           | Критичные операции          | Максимальная актуальность                 | Дополнительная нагрузка        |
| На основе изменений  | Расчеты стоимости           | Эффективность для сложных данных          | Сложная реализация             |
