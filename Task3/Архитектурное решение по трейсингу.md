## Мотивация
Проблемы, которые решит внедрение трейсинга:
1. Клиенты жалуются на "потерянные" заказы и непонятные статусы - трейсинг позволит моментально находить, на каком этапе завис конкретный заказ;
2. Операторы тратят время на поиск проблемных заказов - система покажет всю цепочку обработки заказа в одном интерфейсе;
3. Сообщения между сервисами теряются без следа - трейсинг выявит, в какой момент и почему пропадают сообщения в RabbitMQ;
4. Партнеры (B2B) получают ошибки без объяснения причин - появится возможность показать полный путь обработки их запроса.

## Итоги анализа проблемы
Покрытие систем трейсингом:
1. Онлайн-магазин (Vue + Spring Boot):
- Переходы между статусами заказа (INITIATED → SUBMITTED)
- Загрузка 3D-моделей
2. MES (.NET):
- Расчет стоимости (SUBMITTED → PRICE_CALCULATED)
- Производственные статусы (MANUFACTURING_STARTED → COMPLETED)
3. CRM (Vue + Spring Boot):
- Подтверждение заказа (PRICE_CALCULATED → MANUFACTURING_APPROVED)
4. RabbitMQ:
- Сообщения между CRM и MES
- Dead-letter-очереди
5. API для партнеров:
- Внешние вызовы расчета стоимости

Критические точки:
1. Потеря сообщений в RabbitMQ;
2. Зависание расчета стоимости в MES;
3. Долгое подтверждение перехода в производство в CRM.

## Предлагаемое решение
Используемая технология:
- OpenTelemetry (трассировка) 
- Jaeger (визуализация)

Изменения в архитектуре (выделено красным на [схеме](https://jewerly_c4_model.drawio)):
- Collector для агрегации данных
- Интеграция OpenTelemetry в:
  - Spring Boot (CRM, магазин)
  - .NET (MES)
  - RabbitMQ (через плагин)
- Jaeger UI для поиска трейсов

## Выбор подхода к мониторингу
Будем использовать комбинированный подход:
1. API и пользовательские сценарии - «Четыре золотых сигнала» (Latency, Traffic, Errors, Saturation).
2. Инфраструктура (CPU, память, очереди) - USE (Utilization, Saturation, Errors).
3. RabbitMQ и асинхронные процессы - RED (Rate, Errors, Duration).
