## Мотивация
Проблемы, которые решит внедрение трейсинга:
1. Клиенты жалуются на "потерянные" заказы и непонятные статусы - трейсинг позволит моментально находить, на каком этапе завис конкретный заказ;
2. Операторы тратят время на поиск проблемных заказов - система покажет всю цепочку обработки заказа в одном интерфейсе;
3. Сообщения между сервисами теряются без следа - трейсинг выявит, в какой момент и почему пропадают сообщения в RabbitMQ;
4. Партнеры (B2B) получают ошибки без объяснения причин - появится возможность показать полный путь обработки их запроса.

## Итоги анализа проблемы
Покрытие систем трейсингом:
1. Онлайн-магазин (Vue + Spring Boot):
- Переходы между статусами заказа (INITIATED -> SUBMITTED)
- Загрузка 3D-моделей
2. MES (.NET):
- Расчет стоимости (SUBMITTED-> PRICE_CALCULATED)
- Производственные статусы (MANUFACTURING_STARTED -> COMPLETED)
3. CRM (Vue + Spring Boot):
- Подтверждение заказа (PRICE_CALCULATED -> MANUFACTURING_APPROVED)
4. RabbitMQ:
- Сообщения между CRM и MES
- Dead-letter-очереди
5. API для партнеров:
- Внешние вызовы расчета стоимости

Критические точки:
1. Потеря сообщений в RabbitMQ;
2. Зависание расчета стоимости в MES;
3. Долгое подтверждение перехода в производство в CRM.

## Предлагаемое решение
Используемая технология:
- OpenTelemetry (трассировка) 
- Jaeger (визуализация)

Данные в трейсах:
- order_id
- status_before -> status_after
- timestamp
- service_name
- error (при возникновении)

Изменения в архитектуре (добавленные компоненты выделены красным на [схеме](https://github.com/alexeit-315/architecture-alexandrite/tree/draft-branch/Task3/jewerly_c4_model.drawio)):
- Добавлен OpenTelemetry Collector для агрегации данных
- Интеграция  с OpenTelemetry:
  - Spring Boot (CRM, магазин)
  - .NET (MES)
  - RabbitMQ (через плагин)
- Добавлен Jaeger Collector для приёма, обработки и сохранение трейсов
- Добавлен Jaeger Query для поиска и отображение трейсов через UI
- Добавлен Elasticsearch для хранения трейсов
- Добавлен  Jaeger UI для для визуализации и анализа данных трейсинга

## Компромиссы
Когда трейсинг не поможет:
- Для legacy-части MES доработка кода для использования OpenTelemetry слишком дорога и трудозатратна

Ограничения:
- Трейсинг RabbitMQ требует обновления до версии 3.8+

## Безопасность
Предлагаемые меры:
- Аутентификация в Jaeger через Keycloak
- Ролевая модель:
  - support — только просмотр
  - devops — доступ к raw-данным
- Шифрование трассировочных данных в Transit (TLS)
- Фильтрация ПдН 

## Предлагаемое решение
Предлагается следующая схема автоматического мониторинга процесса прохождения заказа, получения данных трейсинга и алертинга (добавленные компоненты выделены зеленым на [схеме](https://github.com/alexeit-315/architecture-alexandrite/tree/draft-branch/Task3/jewerly_c4_model_v.2(0).drawio)):
- OpenTelemetry Collector производит агрегацию и обогащение/фильтрацию (добавление order_id, маскировка ПдН) данных трейсинга из инструментированных подсистем:
  - CRM
  - Интернет-магазин
  - MES (новый сервис расчета стоимости)
  - Очередь сообщений RabbitMQ
- Jaeger Collector получает собранные данные трейсинга от OpenTelemetry Collector, производит их валидацию (проверка trace_id, order_id) и сохранение в БД трейсинга Jaeger db (Elasticsearch)
- Jaeger Query производит поиск и агрегацию трейсов из хранилища, предоставляет API для Jaeger UI и внешних систем (Grafana) и производит экспорт метрик в Prometheus
- Jaeger UI обеспечивает визуализацию трейсов в виде графа вызовов и временной шкалы, поиск/фильтрация по тегам (order_id, status, duration), веб-интерфейс доступен:
  - Поддержке
  - Разработчикам
  - Менеджерам
- Jaeger Storage (Elasticsearch) производит хранение трейсов с индексацией по:
  - trace_id
  - order_id
  - timestamp
  - duration
- Prometheus обеспечивает сбор метрик с инструментированных компонентов, хранение временных рядов и отправку алертов в Alertmanager при нарушении правил
- Grafana выполняет визуализацию метрик, отображение дашбордов SLA
- Alertmanager производит обработку алертов, их дедупликацию и группировку, маршрутизацию уведомлений в нужные каналы
- Notification Service производит управление каналами уведомлений (Email/SMS/ТГ), шаблонизацию сообщений и ограничение частоты уведомлений
